¿Por qué t3.medium (2 vCPU, 4 GiB) y no t3.micro / t3.small?

Cada instancia levanta simultáneamente 8 JVM (Spring Boot + Eureka + Config + Gateway) y Nginx, consumiendo ≈ 3 GiB con límites de memoria; en t3.small (2 GiB) los contenedores colapsarían por OOM. Las instancias son stateless (comparten RDS y secreto JWT).

2.2 Flujo de Tráfico por Capas y Aislamiento de Internet

Las subredes internas carecen de IP pública; el tráfico entra solo por el ALB y sale de forma controlada por NAT.

Paso 01 · Entrada

Internet → ALB

Único punto expuesto a Internet (80/443) balanceado en dos zonas.

Paso 02 · Aplicación

ALB → EC2 Privadas

Instancias sin IP pública ejecutando el stack de microservicios.

Paso 03 · Datos

App → RDS Privada

Tabla de rutas solo local: la base de datos nunca alcanza ni recibe Internet.

Paso 04 · Salida

App → NAT → IGW

Salida unidireccional segura sin abrir acceso entrante desde Internet.

03 · Estrategia de Migración William David Ortiz

3.2 Elección del Modelo 7R (Replatform) y Plan en 6 Pasos

Replatform permitió conservar intacto el código Spring Boot/Angular mientras se modernizaba la infraestructura limitante.

Por qué NO las otras 6 R

Retire/Retain: el negocio requiere el sistema. Rehost: mantenía MySQL dentro de la EC2. Repurchase/Relocate: no aplican. Refactor: reescribir a serverless excedía el plazo.

Qué cambia con Replatform

MySQL en contenedor → RDS Multi-AZ; disco local → S3 cifrado; servidor único → AMI + ASG + ALB, manteniendo código e imágenes sin cambios.

Sin corte en el origen

El servidor origen permaneció operativo y validado hasta comprobar el hash SHA-256 y los conteos idénticos por el DNS del ALB.

Paso 1

Red y Datos

Desplegar pilas 01-red y 02-datos.

Paso 2

Dump + Hash

mysqldump --single-transaction y SHA-256.

Paso 3

Copia a S3

Subir migracion_u3.sql y estáticos.

Paso 4

Crear AMI

Imagen del servidor con Docker y servicios.

Paso 5

Importar RDS

Desde EC2 privada verificar hash e importar.

Arquitectura propuesta (sin impactar RDS)

05 · Síntesis Final Equipo (Cierre)

5.2 Conclusiones del Proyecto y Recomendaciones Evolutivas

Cumplimiento verificado de las seis exigencias de la guía práctica y hoja de ruta hacia producción continua.

Conclusiones clave

  • Alta disponibilidad y elasticidad: Tolera caída de servidor (reemplazo en 269 s sin corte) y de zona (ALB + RDS Multi-AZ), escalando 2 → 4 → 2 automáticamente.
  • Reproducibilidad IaC: Tres pilas modulares de CloudFormation reconstruyen red, datos y aplicación en minutos.
  • Migración limpia: Estrategia Replatform sin alterar código, integridad SHA-256 exacta y recuperación probada (498 s RTO, 0 RPO).
  • Desacoplamiento: Extraer MySQL del servidor EC2 habilitó instancias intercambiables sin estado.

Recomendaciones (siguiente iteración)

  • Habilitar listener HTTPS (443) con certificado ACM para libreria.hidrocomkallpa.site y redirección 80 → 443.
  • Integrar MFA en el ALB mediante Amazon Cognito sin depender de estado local.
  • Migrar imágenes Docker a Amazon ECR y desplegar mediante instance refresh.
  • Mover imágenes de libros desde ms-book hacia S3 (o EFS) para persistencia multi-instancia.
  • Programar apagado nocturno fuera de horario y ejecutar el piloto Glue + Athena + SageMaker Canvas.
